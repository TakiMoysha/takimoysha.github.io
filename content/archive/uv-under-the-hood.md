Бенчмарки uv показывают ускорение в 10-100x в сравнении с pip. Читая исходники, я смог ответить почему так - "это написанно на rust".

Мы проследим за работой на каждом слое: от структуры репозитория, посмотрим что буквально происходит, когда вы вводите `uv init` или `uv add requests`, вплоть до конкурентных паттернов rust, где и работает резолвер. Это написано для тех, кто хочет понять техническую сторону и кто захочет внести свой вклад. Опыт в rust не приоритетен, но если вы его видели это этого, я укажу на конкретные паттерны в коде.

**uv** - это черезвычайно быстрый пакетный менеджер, написанный на rust и созданый Astral, командой создавшей ruff. Он заменяет большинство утилит в одном бинарнике.

| Old tool              | uv equivalent         |
| --------------------- | --------------------- |
| `pip install`         | `uv pip install`      |
| `pip-compile`         | `uv pip compile`      |
| `virtualenv` / `venv` | `uv venv`             |
| `pyenv`               | `uv python install`   |
| `pipx run`            | `uvx` / `uv tool run` |
| `poetry` / `rye`      | `uv init` + `uv add`  |

### Структура репозитория

```scheme
uv/
├── crates/          # исходники на rust
├── docs/            # MkDocs документация
├── python/          # PyPI wheel, мост для python
├── scripts/         # ,бенчмарки и тулинг
├── test/            # тесты и необходимые файлы для бенчей
├── Cargo.toml       # указывает на корень workspace
└── pyproject.toml   # uv менеджерит сам себя
```

Все основное происходит в `crates/`, rust не разрешает циклические зависимости между крейтами, поэтому код структурируется как направленный ациклический граф направленный на крейты, где каждый отвечает за свой функционал:

```scheme
crates/
├── uv/                  # CLI бинарник - входящая точка, парсинг аргументов
├── uv-resolver/         # резолвер зависимостей (PubGrub)
├── uv-installer/        # устанавливает пакеты в окружение
├── uv-client/           # async http клиент для PyPI и реестров
├── uv-workspace/        # pyproject.toml парсер и поисковик рабочего окружения
├── uv-python/           # менеджер версии Python
├── uv-cache/            # глобальный кеш с адресацией по содержимому
├── uv-distribution/     # колеса и sdist обработчики, работа с метаданными
├── uv-build/            # собственный бекенд сборки (hathling/setuptools)
├── uv-git/              # поддержка git-зависимостей
├── uv-platform-tags/    # сопоставление совместимости колес
├── uv-pep440/           # парсер версии определенной PEP440
├── uv-pep508/           # Парсер зависимостей по PEP508
├── uv-types/            # разделяемый типы
└── ... (прочее)
```

Мы можем сгенерировать визуальный граф зависимостей между крейтами:

```bash
cargo depgraph --dedup-transitive-deps --workspace-only | dot -Tpng > graph.png
```

Ключевая идея в том, что крейт `uv` находится на самом верху и зависит от всего. uv-types находятся почти в самом низу и приктически ни от чего не зависят. Код распространяется только вниз - циклов нет, что обеспечивается на языковом уровне.

### Что происходит при вводе `uv init`

Давайте проследим шаг за шагом, как происходит инициализация пакета:

**Парсинг аргументов**: `uv` использует `clap` для парсинга аргументов. Когда вы запускаете любую команду `clap` определяет подкоммманду, например `init` и резолвит ее по определенным правилам, парсит аргументы и выделяет только нужные флаги (`--lib`, `--app`, `--package`, `--bare`, `--build-backend`, etc.).

**Workspace Discovery**: перед тем, как создать что либо uv проверяет, что уже есть внутри workspace. Он проходит вверх по дереву директорий в поисках `pyproject.toml` с секцией `[tool.uv.workspace]`. Если находит таковую, новый проект создается как член workspace автоматически, в ином случае как самостоятельный пакет.

**Структура проекта**: для `uv init hello-world`, uv использует шаблон простого приложения (`main.py`, `pyproject.toml` и `readme.md`). При этом не указывается `[build-system]` - он не будет собираться как python-пакет. Это позволяет избегать ненужных шагов установки и сложности выбора бекенда для сборки.

Если мы передаем `--lib` или `--package`, uv добавит свою билд-систему.

**Инициализация Git**: если git не определен, то uv запускает `git init` и добавляет `.gitignore` (не перезаписывает и не дописывает) с файлами специфичными для python проектов. Этот шаг можно пропустить передав флаг `--no-vsc`.

> [!note] если нету `venv`, то uv создаст его только при запуске кода или установке.

### Что происходит при `uv add requests`

Основная операция - добавление зависимостей, это происходит как добавление записи в `pyproject.toml` и в `uv.lock`, и установка самого пакета в окружение (при отсутствии оного - создается окружение).

**Чтение структуры проекта**: за это отвечает крейт `uv-workspace`, читает `pyproject.toml` и создает виртуальный структуру - `manifest`. Туда входит имя проекта, зависимости, версия, члены окружения и переопределения.

**Обновление `pyproject.toml`**: uv добавляет пакет как требование, без указания версии. После определения версии (следующий шаг) он добавит нижнюю границу.

Это изменение идет через `project-mut`, указанный в `uv-workspace`, который обеспечивает точное редактирование файлов toml - он вносит исправления толдько в те поля, которые необходимо изменить не изменяя фоматирования остальной части файла. Это важно, т.к. pyproject.toml часто содержит отформатированные вручную разделы, комментарии и специально выбранный порядок элементов.

**Указание версиии (`uv-resolver` + PubGrub)**: resolver отвечает на вопрос - "Какая именно вверсия каждого пакета удовлетворяет всем ограничениям?". Это наиболее сложный шаг. Мы должны погрузимся в тему чуть позже. Выходным значением является `(package, version)` для каждого пакета в дереве зависимостей.

Локфайл кроссплатформен, он работает на всех системах, т.к. это просто текстовый файл. Он записывает все возможные пакеты для всех платформ используя маркеры окружения. Когда вы устанавливаете из зависимости из локфайла на настоящую машину, uv выбирает только необходимые пакеты соответствующие вашей платформе. Это фундаментальное отличие от `pip freeze` или `requirements.txt`.

Хеши в файлы нужны для двух задач: валидация целостности при загрузке и кешированию.

> [!note] локфайл это внутренний формат, специфичный для uv, он может меняться, если вам нужно прочитать его программно, то используйте workspace-метаданные - они выводят стабильное JSON-представление того же графа зависимостей.

**Загрузка пакетов (`uv-client` + Tokio)**: `uv-client` это асинхронный http клиент построенный на `reqwest` и `tokio`. Для каждого пакета, которого нету в глобальном кеше, uv запускает параллельный процесс загрузки.

Это главный фактор влияющий на скорость работы uv при работе с холодным кешем. Задержка сетевого io является узким местом, а параллелизм позвоялет сделать ее практически постоянной независимо от кол-ва пакетов.

Пакеты храняться в глобальном кэше с адресайией по содержимому, управляемом через `uv-cache`:

- любой уже установленный пакет будет переиспользован;
- кеш валидирует пакеты по хешу при каждом использовании - скрытые повреждения обнаруживаются немедленно;
- кеш используется совместно при установке с помощью uv (`uv pip install`, `uvx` , `uv add`, etc.)

**Установка пакет (`uv-installer`)**: установка обычно подразумевает копирование файлов. uv-installer использует более современный подход - он использует жесткие ссылки там, где это поддерживает файловой системой.

> [!tldr] HardLink (`ln`)
> Это механизм создания нескольких ссылок на один и тот же файловый блок на диске. В отличие от `ln -s` (symbolic link), жесткие ссылку исказывают на сам физический блок (inode), а не на ссылку на этот inode.
> Жесткие ссылки могут быть источником "висячих ссылок" (dangling), т.к. физически файл удалиться только при отсутствии на него ссылок.

При установки в `site-packages` uv просто создает жесткую ссылку на зависимость в глобальном кеше. По этому он может установить тысяци зависимостей за пару сотен мс - столько занимает создание ссылок.

Если FS не поддерживает жесткие ссылки (home-dir, temp, mnt), то переключается на ref-ссылки copy-on-write, а затем на обычные копии.

## Deep Dive

#### Двух-поточная архитектура резолвера

**Resolver** - наиболее интересная с архитектурной точки зрения часть uv.

*Проблема конкрурентной среды*. Внутри используется PubGrub, алгоритм является последовательным и синхронным: он принимает одно решение за раз, и каждое решение зависит от всех предыдущих. Вы не можете тривиально распараллелить это.

Алгоритм PubGrub по своей сути является последовательным и синхронным: он принимает одно решение за раз, и каждое решение зависит от всех предыдущих решений. Вы не можете тривиально распараллелить это.

Но запросы от PyPI "какие версии flask существуют" или "зависиомтс flask-3.1.0" - это высокораспараллеливаемый IO.

Наивный подход - сериализовать все: выбрать пакет, получить метаданные, выбрать следующий пакет, получить метаданные. Это делает `pip`.

*Двухпоточная коммуникация через channels* - посмотрите на `crates/uv-resolver/src/resolver/mod.rs` - ф-ция `resolve` показывает как это работает:

```rust
pub async fn resolve(self) -> Result<ResolverOutput, ResolveError> {
    let state = Arc::new(self.state);
    let provider = Arc::new(self.provider);

    // Канал для отправки запросов на извлечение данных от решателя -> модуля извлечения (пропускная способность: 300).
    let (request_sink, request_stream) = mpsc::channel(300);

    // Асинхронный модуль загрузки работает в пуле потоков Tokio.
    let requests_fut = state.clone().fetch(provider.clone(), request_stream).fuse();

    // PubGrub работает в ВЫДЕЛЕННОМ СИНХРОННОМ ПОТОКЕ.
    let solver = state.clone();
    let (tx, rx) = oneshot::channel();
    thread::Builder::new()
        .name("uv-resolver".into())
        .spawn(move || {
            let result = solver.solve(&request_sink);
            let _ = tx.send(result);
        })
        .unwrap();

    let resolve_fut = async move { rx.await.map_err(|_| ResolveError::ChannelClosed) };

    // запуск обоих и ждем завершения одной из них (или ошибки).
    let ((), resolution) = tokio::try_join!(requests_fut, resolve_fut)?;
    resolution
}
```

Поток с решателем работает синхронго, PubGrub не подходит для использования с async/await, т.к. представляет собой плотный цикл со сложным, изменяемым состоянием. Синхронное выполнение в отдельном потоке позволяет избежать расходов, связанных с попыткой сделать асинхроннй решатель.

Фетчер работает в пуле асинхронных потоков tokio. Когда решателю требуются метаданные для пакета, он отправляет запрос по каналу mpsc (capacity 300) и затем проверяет InMemoryIndex (параллельный кеш на основе DashMap). Если результат еще не поступил, он приостанавливается и уступает управление, пока фечер не запишет данные. Поток решателя использует `wait_blocking`, который блокирует только этот поток, а не среду выполнения tokio.

Итого у нас есть четко распределенная ответственность:

- PubGrub работает в синхронном режиме и отличается простотой.
- Сетевой io работает асинхронно и параллельно.
- Объект `Arc<ResolverState>` безопасно совместно используется обеими сторонами.
- Канал mpsc (емкостью 300) создает backpressure - решатель может накопить в очереди до 300 запросов, прежде чем произойдет блокировка.

> [!TLDR] `InMemoryIndex`
> Это разделяемый кеш уже запрошенных метаданных пакетов. Основанный на `DashMap` (конкурентный hashmap, который дает читать без локов всю мапу). Решатель читает из нее, Фетчер пишет в нее. Решатель использует `wail_blocking` что бы приостановить себя пока не будет нужного индекса, без блокировки рантайма.

#### PubGrub - алгоритм определения зависимостей

**Почему это сложно**: resolver должен решить задачу: при заданных зависимостях (с диапазоном версий) найти для каждого пакета одну точную версию, при которой также будут удовлетворены требования всех других пакетов - рекурсивно, для всех транзитивных зависимостей.

В общем случает это эквивалетно задаче булевой удовлетворимости (SAT), которая является NP-полной. Экосистемы пакетов содержат тысячи пакетов и сотни версий каждого из них. Наивный метод обратного прослеживания (перебирать версии пока не заработает) может привести к экспоненциальному росту времени выполнения.

**Conflict-driven clause learning**. uv использует `pubgrub-rs` - реализацию [PubGrub](https://nex3.medium.com/pubgrub-2fb6470504f), разработанную Натали Вайзенбаум для пакетного менеджера Dart в 2018 году. PubGrub - это решатель задач с обученем на основе конфликтов (CDCL).

PubGrub при обнаружении конфликат извлекает из него урок, записывая условие несовместимости. Условие кодирует, какая комбинация версии пакетов вызвала конфликт. Любое будущее состояние, которое вызвало бы тот же конфликт, сразу отсекается без повторного поиска.

Например: Решатель находит, что `a==2.0` и `b==3.0` не могут сосущестовать, т.к. трубют конфликтующих версий `c`. PubGrub Записывает несовместимность. Любое будущее частичное решение, содрежащие оба, мгновенно исключаются. Это превращает экспоненциальные худшие случаи в управляемые для реалистичных графов пакетов.

#### Цикл разрешения

В официальной документации есть описание [как работает resolver](https://docs.astral.sh/uv/reference/internals/resolver/#resolver):

1. *Инициализация* - создание виртуального корневого пакета, представляющего проект. Это единственный "определённый" пакет; всё остальное - неопределённое.
2. *Выбор неопределённого пакета с наивысшим приоритетом*. Порядок приоритетов в uv таков:
   - url-зависимость (git, path, file) - зафиксированные; согласование версий не требуется.
   - пакеты с `==` - версия уже определена.
   - "высококонфликтные" версии (см. ниже).
   - все остальное, упорядоченное по времени первого обнаружения (обход в ширину).
     Это гарантирует, что прямые зависимости определяются раньше транзитивных.
3. *Выбор версии*. По умолчанию uv пробует версии от самой новой к самой старой (или от самой старой к самой новой, если resolution = "lowest"). Предпочтение отдается версиям, уже находящимся в `uv.lock` (что делает повторные разрешения стабильными), и версиям, уже установленным в текущей среде (что позволяет избежать ненужных обновлений).
4. *Добавление требований*. Все требования выбранной версии добавляются в набор нерешенных. uv отправляет запросы на предварительную загрузку их метаданных в фоновом режиме (см. `BatchPrefetcher` ниже).
5. *Обнаружение конфликтов*. Если PubGrub обнаруживает, что выбранная версия создает конфликт, он идентифицирует несовместимую пару, записывает условие несовместимости, возвращается к моменту, когда еще не было принято решение по одной из них, и повторяет попытку с новым ограничением.
6. *Повтор или завершение*. Если для всех пакетов определены версии - успех. Если несовместимость распространяется обратно к корню - сбой с объяснением.

#### Эвристика приоритета конфликтов

В исходниках есть `const CONFLICT_THRESHOLD: usize = 5;`, какой сценарий она разрешает:

Пакет `A` имеет высокий приоритет и выбирается первым. Каждая версия `B` которую проверяет механизм разрешенияконфликтов, немедленно отклоняется из-за конфликат с `A`. Механизм исчерпывает все версии `B`, прежде чем осознает, что первопричинной является выбранная версия `A` - это занимает много времени.

После `CONFLICT_THRESHOLD` в которых участвуют `A` и `B`, uv помечает их как "сильно конфликтующие" и повышает приоритет `B` выше `A`. Затем он возвращает к моменту до принятия решения по `A` и сначале пробует `B`. Принятие решения по пакету с ограничениями в первую очередь позволяет найти правильное решение гораздо быстрее.

#### Ошибки

Когда разрешение конфликта проваливается, pubgrub может воспроизвести почему, вместо `conflictinbg requirements detected` вы получите:

```text
× No solution found when resolving dependencies:
╰─▶ Because my-project depends on flask>=3.0 and flask>=3.0 requires
    werkzeug>=3.0, my-project requires werkzeug>=3.0.
    And because legacy-lib==1.0 requires werkzeug<2.0, and my-project
    depends on legacy-lib==1.0, my-project's requirements are
    unsatisfiable.
```

PubGrub проходит по несовместимной цепочки в обратном порядке последовательно рассказывая что произошло.

#### Предварительная загрузка: boto3

**`BatchPrefetcher`** из `crates/uv-resolver/src/resolver/bach_refetch.rs` это оптимизированная версия загрузчика с большим кол-вом версий, которые вызвает много обратных проходов - типичный пример `boto3/botocore/urllib3`.

Проблема, что при отказе в версии, нужно загружать другую. Для `botocore` это означает сотни последовательных циклов "загрузка-отклонение" при холодном кеше.

Что бы попроавить это резолвер неуспешно пробует `5` раз версии пакета, отправляет запросы на извлечение следующих 50 совместимых версий.

```rust
// после 5, 10, 20, 40 версий, prefetch грузит столько версий, чтобы начать раньше
// но не слишком агрессивно. Затем prefetch 50 выерсий каждые 20
// версий, этого достаточно чтобы полностью загрузить пул задач.
let do_prefetch = (num_tried >= 5  && previous_prefetch < 5)
    || (num_tried >= 10 && previous_prefetch < 10)
    || (num_tried >= 20 && previous_prefetch < 20)
    || (num_tried >= 20 && num_tried - previous_prefetch >= 20);
```

`prefetch` использует две стратегии:

- *стратегия совместимости*: загрузка версий впределах текущего диапазона ограничений, начиная с самой новой и далее вниз.
- *стратегия порядка запуска*: при исчерпании диапазона совместимости, загружается следующая варсия в порядке выпуска, игнорируя совместимость.

Так `prefetch` избегает предваритальной загрузки src-ов (которые трудно собирать) и колес, требующих сборки из исходников. Когда метаданные недоступны через запросы диапазона. Это эвристические методы - они могут загрузать нерелевантные версии - но в случае с холодным кешем `botocore` они могут превратить сотни последовательных обращений в несколько пакетных.

#### Resolver с ветвлением: lock-файл для всех платформ

```toml
numpy>=2,<3 ; python_version >= "3.11"
numpy>=1.16,<2 ; python_version < "3.11"
```

Что бы получить кроссплатформены lock файл обычный resolver не подойдет. Более того, сам python не допускает установки разных версий пакета (как js). *uv-resolver* обнаруживает, что два требования для numpy имеют разные маркеры среды, и разделяет (резветвляет) процесс разрешения на два независимых подпроцесса:

- fork `python_version >= "3.11"` -> резолвит numpy к `2.3.0`
- fork `python_version < "3.11"` -> резолвит numpy к `1.14.4`

Оба рузультата попадают в uv.lock с соответствующими метками. При установки файла блокировки на реальной машине uv сверяет метки с фактической версией python и устанавливает только нужный пакет.

Ветвления могут быть вложенными: само ветвление может быть разделено на другие маркеры, что приводит к дереву решений. Ветка с идентичными пакетами объединяются, что бы lock-файл не разрастался. Точки ветвления записываются в `uv.lock`, что бы повторное решение давало стабильные, идентичные ветвления, а не перерасчитывали их с нуля.

#### Предположение о согласованности метаданных

uv делает одно важно предположение, которое позволяет значительно оптимизировать произодительность: все колеса одной версии пакета имеют идентичные metadata-файлы.

Для `numpy 2.3.2` есть 73 колеса (для разных ос, версий python и архитектур). Без предположения о согласованности метаданных uv пришлось бы запрашивать метаданные из каждого колеса отдельно - это 73 сетевых запроса одной версии.

Благодаря этому допущению uv извлекает метаданные из любого одного колеса (отдавая предпочтение тому, которое поддерживает диапазоны или предоставляет доступ к metadata через PEP 658) и использует их для всех платформ.

На практике это допущение справедливо для всех основных пакетов. Стандарты упаковки Python формально не требуют этого, и в настоящее время идет дискуссия о том, следует ли вводить это требование в обязательном порядке - но ставка uv окупилась.

#### Глобальный Кеш

*Адресная организация контента*: пакеты хранятся и извлекаются по их хешу SHA-256, а не по имени или версии, а следовательно:

- два проекта использующие `requests=2.32.2`, совместно используют одну копию на диске;
- проверка целостности не требует дополнительных затрат - хеш сам по себе является ключом;
- переименование или перемещение кеша безопасно - ничто не зависит от пути.

Структура кеша:

```scheme
~/.cache/uv/
├── wheels/        # колеса по хешу
├── sdists/        # исходники
├── builds/        # колеса из sdists (кешируются после сборки)
├── interpreter/   # метаданные Python интерпретатора (version, sysconfig, etc.)
└── simple/        # "простые" PyPI индексы http ответов
```

**`simple/`** - индексы PyPI - html страница, на которой перечислены все доступные версии пакета. UV кэширует эти ответы. При повторном разрешении с существующим файлом `uv.lock` часто может пропустить все запросы в PyPI - он знает, какие весии были выбраны в прошлый раз, проверяет кеш `simple` на наличие более новых версий и в большинстве случаем (если с момента последней фиксации не было новых выпусков) генерирует идентичное решение без каких-либо сетевых запросов.

```bash
uv cache dir     # вывесит локацию
uv cache prune   # удалить сущности без ссылок на окружение
uv cache clean   # удалить все сущности
```

#### Исходники и песочница для сборки

Если исходники идут только через исходники (нет колес для платформы), uv должен скомпилировать колесо. За это отвечает `DistributionsDatabase` из `uv-distribution`.

Сборка `sdist` подразумевает запуск механизма сборки пакета в изолированной среде. Это разумное требование безопасности т.к. скрипты могут выполнять произвольный код.

uv кеширует успешно собранные колеса в `$XDG_CACHE_HOME/uv/builds/` с ключом соответствующим хешу `sdist`.

В руководстве рекомендуется использовать контейнеры, при сомненях в пакете:

```bash
podman build -t uv-builder -f crates/uv-dev/builder.dockerfile --load .
podman run --rm -it -v $(pwd):/app uv-builder \
  /app/target/x86_64-unknown-linux-musl/profiling/uv-dev \
  resolve-many /app/scripts/popular_packages/pypi_10k_most_dependents.txt
```

Это важно и для самой разработки uv: если вы проводите тестирование резолвера на 10к самых популярных пакетов PyPI, то в некоторых из них запускается код, который может повлиять на вашу систему.

## Почему именно Rust

- **Гибридная модель выполнения:** Возможность использовать синхронный поток для тяжелых вычислений (PubGrub) и асинхронную подсистему Tokio для I/O внутри одного процесса. Это обеспечивает безопасность данных через `Arc<T>` и каналы, чего сложно достичь в Python при смешивании потоков и async.
- **Предотвращение гонок данных на этапе компиляции:** Собственные правила владения памятью Rust выявляют date race на этапе компиляции. Для безопасного доступа к общим данным используется `DashMap`, который гарантирует корректность многопоточности без необходимости писать явный код синхронизации.
- **Отсутствие задержек из-за GC:** В отличие от Python, Java или Go, Rust освобождает память детерминированно в конце области видимости переменной. Это исключает непредсказуемые задержки (GC pauses), критичные для задач с целью разрешения менее чем за секунду.
- **Прямой вызов системных примитивов:** Операции файловой системы (например, создание жестких связей через `linkat`) выполняются напрямую через syscall без накладных расходов интерпретатора или диспетчеризации модулей ОС, характерных для Python.
- **Zero-Cost Async:** Компилятор Rust трансформирует асинхронный код в машины состояний на этапе компиляции. Это дает производительность, сравнимую с ручным написанием кода на C, позволяя запускать тысячи одновременных задач без накладных расходов на виртуальную диспетчеризацию или выделение памяти.

## Сборка из исходников и contributing

```bash
# сборка и запуск локальной версии
cargo run -- --version
cargo run -- pip install requests
cargo run -- venv

cargo install cargo-nextest

cargo nextest run

# запуск конкретного теста
cargo nextest run -E 'test(test_add_requirement)'

cargo insta test --accept --test-runner nextest
```
