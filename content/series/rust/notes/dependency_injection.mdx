Реализация dependency injection в rust усложняется отсутствием runtime reflection - нету динамического определения типов и структур данных во время выполнения, как в java или C#.

Что охватывате:
* Концепция внедрения зависимостей и ее преимущества
* Как другие языки реализуют DI
* Уникальные проблемы и сильные стороны Rust при реализации DI
* Пошаговое руководство по созданию собственного DI-контейнера в Rust

Бонусы от DI:
* *Testability*: упрощает использование mock или stubs в тестах, что позволяет проводить более изолированные и контролируемые тесты;
* *Decoupling of components*: DI уменьшает связанность между компонентами, делая код более модульным и простым в обслуживании;
* *Easier Maintenance*: с DI можно изменить реализацию зависимости, без изменения компонента, который ее использует, что улучшает сопровождение и адаптируемость кода.

**Benefits of a Manual Dependency Container:**
* Лучше понимание, что происходит в фреймворке и "позади сцены".
* Мы можем установить закономерности того, как действовать в определенных случаях, наблюдая повторение событий, происходящих в общей группе случаев. Это важно, поскольку закладывает основу для превращения повторяющихся действий в макросах.
* Мы продвигаем все ошибки в отсутствующих зависимостях к ошибкам времени компиляции.

**Requirements for Rust Dependency Container** - перед тем как погрузится, давайте обрисуем ключевые требования и концепции. Они созданы для того, чтобы использовать сильные стороны Rust и одновременно решать уникальные проблемы реализации DI в Rust.

*Compile-Time Safety and Performance*:
* Все ошибки должны быть на уровне компиляции для сохранения rust-ских гарантий безопасности.
* Контейнер должен поддерживать ленивые вызовы зависимостей для оптимизации.
*Flexibility and Usability*:
* Поддержка возврата конкретных типов, трейтов, и динамических трейтов. Более того, мы будем избегать использовать DX для обхода generics. Generics делают кодовую базу сложнее для чтения и для передачи контейнера.
* Возможность обрабатывать вложенные зависимости без сложного api для разработчиков.
* Поддержка условных зависимостей на основе конфигурации среды выполнения.

**Lifetime Management**:
Важный аспект нашего контейнера - управление временем жизни объектов. Для полнимания важности:

> Представим, наш `DataCollector` оказался чем-то, что выбирает данные из БД. А наш сервер это служба, которая проверяет уведомления каждую минуту. Мы могли бы запрашивать `MonitoringSystem` каждую 1 минуту - это значит построение всего дерева зависимостей для `MonitoringSystem` каждую минуту. Т.к. соединение с БД является одной из этих зависимостей, мы также будем каждую минуту устанавливать для него новое соединение. А это ненужные накладные расходы. Было бы лучше подключить БД один раз при запуске программы или в первый раз, когда запрашивается объект, а затем переиспользовать объект по требованию.

Этот пример демонстрирует почему мы нуждаемся lifetime стратегии для наших зависимостей. Основываясь на этой потребности, наш контейнер должен поддерживать три основных времени жизни зависимостей:
* *Singleton*: объекты, созданные один раз и используемые в течение всего срока работы приложения. Примеры включают подключения к базе данных, менеджеры конфигурации и глобальные средства регистрации.
* *Scoped*: объекты, привязанные к определенному объему работы, например одиночный запрос в веб-приложении или один запуск пакетного процесса. Примеры включают идентификаторы запросов, пользовательские контексты или средства ведения журнала.
* *Transient*: новые экземпляры создаются каждый раз, когда их запрашивают. Обычно это легковесные объекты, такие как DTO, средства форматирования или генераторы идентификаторов.

Дополнительные возможности:
* поддержка асинхронные зависимости.
* возможность вернуть `dyn Trait` тип для полиморфизма во время выполнения.

## To Practice: Dependency Container

```rust
impl<T: DataCollector + ?Sized> DataCollector for Box<T> {
    fn collect_data(&self) -> Vec<String> {
        (**self).collect_data()
    }
}

impl DependencyContainer {
    fn create_data_collector_impl_error(&self) -> impl DataCollector {
        if false {
            SimpleDataCollector::new("api_key".to_string())
        } else {
            SqlDataCollector::new("connection_string".to_string())
        }
    }
}
```

Этот код приведет к ошибке компиляции "if" и "else" с несовместимыми типами. Это связано с тем, что тип возвращаемого значения impl является синтаксическим сахаром для общего типа возвращаемого значения, почти. Таким образом, блок в предыдущем разделе заменяет возвращаемый тип `impl DataCollector` на `SimpleDataCollector`. Но тут у нас есть `SimpleDataCollector` и `SqlDataCollector`, поэтому компилятор не знает, чем заменить возвращаемый тип `impl DataCollector`. Решение состоит в том, чтобы вернуть `dyn DataCollector`.

Это дает новый размер, неизвестный во время компиляции. Возвращая тип dyn, мы переключаемся со статической диспетчеризации на динамическую. Исправление состоит в том, чтобы вместо этого обернуть динам в коробку. Таким образом, следующее позволяет нам возвращать признаки dyn, которые позволяют выбирать конкретный DataCollector во время выполнения.

### Transient Dependencies
Пот *transient dependency* понимается легкая зависимость, которую мы можем пересоздать при необходимости.
